# Ticketmaster

상태: 1차 학습 정리 완료 · 추가 복습 예정

학습 날짜: 2026-10-12 (한국 시간)

참고 자료: https://www.hellointerview.com/learn/system-design/problem-breakdowns/ticketmaster

오늘 진행한 시스템 설계 모의 면접을 바탕으로 정리한 학습 노트다. 핵심 주제는 좌석 임시 확보, 중복 판매 방지, 대기열, 장애 복구와 멱등성이다. 참고 자료의 전체 설계를 요약한 글은 아니며, 오늘 다루지 않은 항목은 별도 학습 과제로 남긴다.

> 중복 판매는 DB의 조건부 상태 변경으로 막고, 대기열은 부하를 줄이며, 요청 ID는 재시도의 중복 처리를 막는다.

## 나의 학습 노트

### 면접에서 정한 요구사항

- 이벤트 목록을 페이지 단위로 조회한다.
- 공연을 선택하고 좌석 목록을 조회한다.
- 좌석 선택 시 5분 동안 임시 확보한다.
- 외부 결제 서비스의 성공·실패 결과에 따라 예매를 확정하거나 확보를 해제한다.
- 같은 공연의 같은 좌석이 두 사람에게 판매되면 안 된다.
- 인기 공연에서는 대기열로 예매 영역의 입장 인원과 입장 속도를 제한한다.

결제 시스템 내부 구현은 범위에서 제외했다. 그러나 결제 결과와 예매 상태의 연결, 확정 실패 시 결제 취소·환불 요청은 설계에 포함한다. 규모 예시는 좌석 5만 개에 사용자 100만 명이 몰리는 상황이었다. 실제 트래픽 수치나 DB 처리 용량을 측정한 것은 아니다.

### 잘 이해한 부분과 답변 교정

| 실제 답변 요지 | 평가·교정 |
|---|---|
| 결제 후 다른 사람이 예매했다고 알게 되면 UX가 나쁘므로 임시 확보 | 임시 확보의 사용자 경험 측면을 잘 설명했다. 만료가 필요한 이유까지 함께 말하면 더 좋다. |
| Redis 키가 없으면 새 키를 저장 | 조회 후 저장의 경합이 빠졌다. 이후 Lua로 원자적 처리하는 방향을 제안했다. |
| 해제 시 고유 예약 토큰으로 본인의 점유인지 확인 | 소유권 검증을 이해했다. 비교·삭제의 원자성까지 포함해야 한다. |
| TTL이 지났으면 A의 결제 실패로 간주 | 예매 확정 거절과 이미 성공한 결제의 취소·환불을 구분해야 한다. |
| `WHERE expiresAt > currentTime()`만으로 확정 | 대상 예약, 소유권 토큰, 현재 상태 조건이 빠져 있었다. |
| expiresAt이 현재 시간보다 크면 시간 초과 | 부등호가 반대다. 크면 아직 유효하고, 작거나 같으면 만료다. |
| 두 번째 결제 알림은 이미 CONFIRMED이므로 완료 응답 | 멱등 처리 방향은 맞다. 동일 결제 ID와 저장된 성공 결과를 확인해야 한다. |
| ACID이므로 조회·UPDATE를 원자적으로 묶음 | 트랜잭션만으로 충분하다고 단정할 수 없다. 조건부 갱신·잠금·제약을 명시해야 한다. |
| `SELECT ... FOR UPDATE`로 버전 충돌 해결 | 유효한 대안이지만 낙관적 제어가 아닌 비관적 잠금이다. |
| `SET status = ... AND version += 1` | SET 항목은 쉼표로 구분하고 `version = version + 1`을 사용한다. WHERE에 기대 버전도 필요하다. |
| 갱신 0개면 이미 처리된 요청 | 내 요청의 중복 성공인지, 다른 사용자의 선점인지 구분해야 한다. |
| 대기열로 중복 판매 방지 | 대기열은 부하 제어다. 중복 판매의 최종 보장은 DB 동시성 처리다. |
| 헤더에 대기열 통과 토큰임을 명시 | 헤더·필드는 사용자가 만들 수 있다. 이후 사용자·공연 ID를 서명하겠다고 보완했다. |
| DB 확보 성공 후 Redis 반영 실패여도 성공 반환 | DB를 최종 기준으로 삼은 설명이 좋았다. 트랜잭션이 모든 업무 오류를 제거하는 것은 아니라는 점을 보완한다. |
| 알림 retry로 확보 응답 유실 처리 | 전달 재시도와 확보 요청의 멱등성을 구분해야 한다. |
| 고유 예약 토큰을 DB에 저장해 재요청 식별 | 식별자 저장 방향은 맞지만 응답 전에도 클라이언트가 아는 요청 ID가 필요하다. |

힌트 없이 잘 설명한 부분은 임시 확보의 필요성, 토큰 소유권 확인, 대기열 도입 이유였다. 조건부 SQL, 반환 행 수의 의미, DB 기준 설계와 멱등성은 면접관의 설명·힌트를 거쳐 보완했다. 전체 설계를 처음부터 독립적으로 완성했다고 평가하지 않는다.

### 간단한 면접 히스토리

| 단계 | 논의 내용 | 도달한 결론 |
|---|---|---|
| 요구사항 | 이벤트 조회·좌석 예매·결제 범위 | 결제 내부는 제외, 결제 결과 처리는 포함 |
| 임시 확보 | 사용자 경험과 만료 | 5분 확보 |
| 동시성 | Redis 조회·저장, Lua | 원자적 확보와 토큰 기반 해제 |
| 만료·결제 | 늦은 알림과 상태 확인 | 확정 조건 검사, 필요 시 환불 |
| DB 갱신 | 상태·버전·토큰, 행 수 | 조건부 갱신과 경합/중복의 구분 |
| 장애 | Redis 유실과 DB 상태 | DB가 최종 기준 |
| 트래픽 | 대기열, Kafka, Sorted Set | 입장 제어와 별도 대기 상태 관리 |
| 접근 | 입장 토큰의 헤더·서명 | 사용자·공연·만료 검증 |
| 전체 흐름 | DB 커밋과 캐시 반영 | DB 성공 후 캐시 실패 복구 |
| 재시도 | 알림 retry와 예약 토큰 | 클라이언트 요청 ID와 저장된 결과 |

이벤트 목록의 상세 인덱스, 용량 계산, 다중 리전, 다중 좌석 원자성, 환불 작업의 내구성은 충분히 평가하지 않았다.

## 핵심 개념과 트레이드오프

### 오늘 설계의 핵심 원칙

| 장치 | 해결하는 문제 | 이 장치만으로 보장하지 않는 것 |
|---|---|---|
| DB 조건부 갱신과 제약조건 | 좌석 소유권과 상태 변경의 정확성 | 잘못 작성한 조건이나 업무 로직까지 자동 교정하지 않음 |
| Redis 분산 락·캐시 | 경합·조회 부하 감소, 빠른 임시 상태 조회 | Redis 키의 존재만으로 최종 예매 여부를 확정하지 않음 |
| 대기열 | 예매 서비스와 DB로 향하는 요청량 제어 | 입장한 사용자끼리의 좌석 중복 판매 방지 |
| 서명된 입장 토큰 | 대기열 우회와 다른 공연 접근 방지 | 특정 좌석의 확보 소유권 |
| 예약 토큰 | 특정 확보의 소유권 확인 | 클라이언트가 토큰을 받기 전 발생한 응답 유실의 재시도 식별 |
| 멱등성 요청 ID | 같은 요청의 재전송과 결과 재사용 | 같은 키로 다른 요청 내용을 처리하는 것 |

**입장 토큰, 예약 토큰, 요청 ID는 서로 다른 목적의 식별자다.**

### Redis 원자성, 토큰, 만료

처음 제안한 “키가 없으면 저장” 방식은 조회와 저장을 별도 명령으로 실행하면 경쟁 상태가 생긴다. 키 존재 검사와 TTL을 포함한 저장을 원자적으로 수행해야 한다. 오늘은 Lua 스크립트로 이 동작을 묶는 방법을 답변했다.

키는 공연별 좌석을 구분하고, 값은 확보 요청마다 발급한 고유 예약 토큰으로 둔다. 취소 시 **값이 내 예약 토큰과 일치할 때만 삭제**한다. 비교와 삭제도 원자적으로 묶는다.

예를 들어 A의 키가 만료된 뒤 B가 같은 좌석을 확보했을 때, A의 늦은 취소가 키를 무조건 삭제하면 B의 확보가 사라진다. 토큰 비교가 이 문제를 막는다.

Redis가 장애나 재시작으로 키를 잃어도 DB에 유효한 `HELD` 상태가 있으면 다른 사용자의 확보를 거절한다. 반대로 Redis에 키가 있다고 DB 상태까지 최신이라고 보장할 수도 없다.

**최종 확보 성공은 DB 트랜잭션의 커밋 결과를 기준으로 한다.** Redis 반영 실패 시 캐시 무효화·재시도·DB 조회로 보완한다. Redis를 캐시로 사용할 때는 장애 시에도 DB의 동시성 검사를 생략하지 않는다.

### 늦은 결제와 중복 결제 알림

확보할 때 마감 시간을 기록한다. 남은 TTL에 현재 시간을 계속 더해 새 마감 시간을 만드는 방식보다, 명시적인 만료 시간으로 판단하는 것이 명확하다.

오늘 면접에서 채택한 단순화된 정책은 **예매 확정 시점에 확보가 만료됐으면 확정하지 않는다**는 것이다. 이미 외부 결제가 성공했다면 이를 “결제 실패”로 덮어쓰지 않고 취소·환불 절차를 요청한다. 이미 B가 확보한 좌석에는 영향을 주지 않는다.

실무에서 “결제는 기한 내 성공했지만 알림만 늦게 도착한 경우”를 허용할지는 별도의 정책이다. 결제 준비 상태, 유예 시간 또는 결제 시각 검증 등의 설계가 필요하며, 오늘 면접에서는 깊게 다루지 않았다.

동일한 결제 성공 알림이 두 번 오면:

1. 첫 요청에서 결제 ID와 예매 확정 결과를 저장한다.
2. 재요청에서 동일한 결제 ID로 이미 확정된 예약인지 확인한다.
3. 같은 결제라면 기존 성공 결과를 반환한다. 중복 티켓 발급·환불을 수행하지 않는다.
4. 조건부 UPDATE가 0개였다는 이유만으로 만료나 성공 중 어느 하나라고 단정하지 않는다.

### 대기열과 입장 권한

#### 대기열의 역할

대기열은 100만 명이 동시에 좌석 확보 API를 호출하는 상황을 완화한다. 입장 속도와 예매 영역의 활성 사용자 수를 서버·DB 처리 용량에 맞춰 제어한다. 입장한 사용자의 반복 요청도 고려해야 한다.

최종 제안은 Redis Sorted Set에 대기 사용자를 넣고 접속 시간으로 순서를 정하며, 클라이언트가 대기 상태를 폴링하는 구조였다.

추가 고려사항:

- 동일한 시간값을 가진 요청의 순서를 정의한다.
- 폴링 간격과 지터로 폴링 자체가 부하를 만들지 않도록 한다.
- 재접속·다중 탭·이탈 사용자의 대기 순서와 입장 상태를 관리한다.
- Kafka는 대기 요청 이벤트 처리에 활용할 수 있지만 순번, 사용자 상태, 입장 권한을 별도로 관리해야 한다. 파티션 여러 개의 순서는 전체 대기열 순서와 같지 않다.

#### 입장 토큰

입장을 허용할 때 사용자 ID, 공연 ID, 만료 시간, 토큰 용도를 담은 서명된 토큰을 발급한다. 면접에서는 만료 시간 30분을 예로 들었다. 이는 좌석 임시 확보의 5분과 다르다.

좌석 확보 API는 서명을 검증하고 사용자 ID가 로그인 사용자와 같은지, 공연 ID가 요청 공연과 같은지, 만료되지 않았는지 확인한다. “대기열 통과”라는 헤더 이름이나 필드만으로는 권한을 인정하지 않는다.

### 응답 유실과 멱등성

알림 재시도는 결과 전달을 돕지만, 좌석 확보 요청의 중복 실행 자체를 막지는 않는다.

클라이언트는 **첫 요청을 보내기 전에** 요청 ID를 만든다. 네트워크 재시도에도 같은 ID를 사용한다. 서버가 성공 응답에서 처음 알려주는 예약 토큰은 응답이 유실되면 클라이언트가 모를 수 있으므로, 이것만으로 재시도를 식별할 수 없다.

서버는 좌석 확보와 같은 트랜잭션으로 다음을 저장한다.

- 로그인 사용자 ID와 요청 ID
- 공연·좌석 등 요청 내용 또는 정규화한 내용의 해시
- 처리 상태와 예약 ID
- 반환할 확보 토큰, 만료 시간, 결과

같은 사용자·요청 ID·내용이 다시 오면 기존 결과를 반환한다. 같은 ID에 다른 내용이 오면 거절한다. 처리 중인 요청은 새 예약으로 중복 실행하지 않는다. 재조회 시 확보가 이미 만료됐다면, 과거 확보 성공 결과와 현재 상태도 구분해 안내한다.

## 예제와 다이어그램

### 좌석 상태와 데이터 모델

```text
AVAILABLE ──확보 성공──> HELD ──유효한 결제·확정──> CONFIRMED
                          │
                          └──만료·취소──> AVAILABLE
```

좌석이 다시 `AVAILABLE`이 되더라도 이전 예약 기록은 `EXPIRED` 또는 `CANCELLED`로 남길 수 있다. 좌석의 현재 상태와 과거 예약의 상태를 구분해야 한다.

면접에서는 `reservation`이라는 이름을 좌석 상태 행에도 사용했다. 실제 구현에서는 다음처럼 역할을 나누면 혼동이 줄어든다.

| 데이터 | 주요 필드와 제약 |
|---|---|
| `event_seat` | 공연별 좌석 하나당 행 하나. `(event_id, seat_id)` 기본 키, 상태, 현재 예약 ID, 확보 토큰, 만료 시간, 버전 |
| `reservation` | 예약 ID, 사용자, 공연·좌석, 예약 상태, 결제 ID. 이전 예약 이력 보관 |
| `idempotency_request` | 사용자, 요청 ID, 요청 내용의 해시, 예약 결과. `(user_id, request_id)` 유일 제약 |

이 표는 면접 내용을 정리하기 위해 제안한 모델이며, 오늘 완성한 실제 DB 스키마는 아니다. 여러 좌석을 한 번에 예약하는 모델은 별도 설계가 필요하다.

#### 임시 확보: 낙관적 동시성 제어

아래는 개념을 설명하는 SQL이다. 바인딩·시간 함수는 사용하는 DB에 맞춰 정해야 한다. `:dbNow`는 클라이언트가 제공한 시간이 아니라, 갱신 시점의 신뢰할 수 있는 DB 기준 시간이다.

```sql
UPDATE event_seat
SET status = 'HELD',
    reservation_id = :reservationId,
    hold_token = :reservationToken,
    hold_expires_at = :expiresAt,
    version = version + 1
WHERE event_id = :eventId
  AND seat_id = :seatId
  AND status = 'AVAILABLE'
  AND version = :expectedVersion;
```

두 요청이 모두 버전 7을 읽었더라도, 먼저 성공한 요청이 상태와 버전을 바꾸면 뒤의 요청은 기존 조건을 만족하지 못한다.

- 영향받은 행 수 1: 이번 요청이 좌석을 확보했다.
- 영향받은 행 수 0: 조건 불일치. 다른 요청의 선점, 상태 변경, 버전 변경, 대상 행 없음 등을 확인해야 한다.
- **0이라고 해서 내 요청이 이미 성공했다고 판단하지 않는다.** 같은 요청의 성공 여부는 별도로 저장한 요청 ID의 결과로 확인한다.

#### 예매 확정

```sql
UPDATE event_seat
SET status = 'CONFIRMED',
    version = version + 1
WHERE event_id = :eventId
  AND seat_id = :seatId
  AND reservation_id = :reservationId
  AND hold_token = :reservationToken
  AND status = 'HELD'
  AND hold_expires_at > :dbNow;
```

외부 결제 성공을 검증한 뒤 이 갱신을 수행한다. 예약 기록의 확정 상태와 결제 ID도 같은 DB 트랜잭션에 기록한다. 각 예약 행만 검사해서는 같은 좌석에 유효한 예약이 두 개 생기는 문제를 막지 못하므로, 공연별 좌석의 단일 상태 행이나 적절한 유일 제약을 함께 사용한다.

#### 비관적 잠금과의 차이

- 낙관적 제어: `WHERE version = :expectedVersion`으로 변경 여부를 검사하면서 갱신한다.
- 비관적 잠금: 트랜잭션 안에서 `SELECT ... FOR UPDATE`로 좌석 행을 잠그고, 잠금을 얻은 뒤 현재 상태를 확인하여 갱신한다.
- `BEGIN`과 `COMMIT`만 추가한다고 경합이 해결되는 것은 아니다. 격리 수준, 잠금 또는 조건부 갱신을 구체적으로 정해야 한다.

### 복습 순서와 질문

#### 우선순위 1 — 조건부 UPDATE와 상태 전이

빈 화면에서 좌석 확보와 확정 쿼리를 각각 작성한다. 각 WHERE 조건이 빠졌을 때 생길 문제를 설명한다.

1. 두 요청이 버전 7을 읽었을 때 한 요청만 성공하는 이유는 무엇인가?
2. 영향받은 행 수 0에서 알 수 있는 것과 알 수 없는 것은 무엇인가?
3. 이전 예약의 EXPIRED 상태와 좌석의 AVAILABLE 상태는 어떻게 다른가?

#### 우선순위 2 — 멱등성·만료·결제

4. 입장 토큰, 확보 토큰, 요청 ID의 발급 시점과 역할을 구분할 수 있는가?
5. DB 커밋 직후 응답이 유실되면 재시도에 어떤 결과를 반환해야 하는가?
6. 같은 요청 ID에 다른 좌석이 들어오면 어떻게 처리할 것인가?
7. 결제 성공이 기한 전에 일어났지만 알림만 늦게 도착한 경우 어떤 정책을 택할 것인가?

#### 우선순위 3 — 장애와 부하 제어

8. Redis 키가 없거나 오래됐을 때에도 DB에서 중복 확보를 막는 이유는 무엇인가?
9. 입장 토큰을 다른 사용자나 공연에 재사용하면 어느 조건에서 거절되는가?
10. 대기열 입장 속도를 어떤 지표로 조절하고 폴링 부하는 어떻게 제한할 것인가?
